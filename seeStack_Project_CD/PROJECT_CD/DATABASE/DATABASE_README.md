# seeStack — Database

seeStack uses two data stores:

- **PostgreSQL 16** for relational application state: users,
  projects, API keys, monitor configuration, grouped errors,
  security scan results, basic load test results, and cached AI
  analyses.
- **ClickHouse 24** for append-heavy time-series telemetry:
  raw error events, monitor checks, logs, HTTP request telemetry,
  cron pings, SSH audit logs, and session replay events.

The CD keeps consolidated schema files for review:

- `schema.sql` — the current PostgreSQL schema, equivalent to the
  backend Flyway migrations `V1__schema.sql` through
  `V4__security_scan_analysis.sql`.
- `clickhouse_schema.sql` — the ClickHouse schema created by the
  backend's `ClickHouseSchemaInitializer` at startup.

## PostgreSQL tables

The current application schema contains eight application tables:

```
users ──owns──▶ projects ─┬─owns──▶ api_keys
                          ├─owns──▶ monitor_configs ──referenced by──▶ load_tests
                          ├─owns──▶ error_groups ─────cached by───────▶ ai_error_analyses
                          ├─owns──▶ security_scans
                          └─owns──▶ load_tests
```

Flyway also creates `flyway_schema_history` to track applied
migrations.

### `users`

Internal account table for email + password authentication.

| Column          | Type          | Notes                            |
| --------------- | ------------- | -------------------------------- |
| `id`            | UUID PK       | Generated by PostgreSQL          |
| `email`         | VARCHAR unique| Normalised to lowercase on write |
| `password_hash` | VARCHAR       | BCrypt hash                      |
| `name`          | VARCHAR       | Optional display name            |
| `created_at`    | TIMESTAMPTZ   | Creation timestamp               |

### `projects`

A user owns one or more projects. Most application records are scoped
to a project.

| Column       | Type          | Notes                            |
| ------------ | ------------- | -------------------------------- |
| `id`         | UUID PK       |                                  |
| `user_id`    | UUID FK users | `ON DELETE CASCADE`              |
| `name`       | VARCHAR       |                                  |
| `slug`       | VARCHAR(100)  | Unique per user                  |
| `platform`   | VARCHAR(100)  | Free-form tag such as `node`     |
| `created_at` | TIMESTAMPTZ   |                                  |

### `api_keys`

Project ingest keys used by the SDKs. Only the SHA-256 hash is
stored; the raw key is shown once when it is created.

| Column         | Type              | Notes                        |
| -------------- | ----------------- | ---------------------------- |
| `id`           | UUID PK           |                              |
| `project_id`   | UUID FK projects  | `ON DELETE CASCADE`          |
| `key_hash`     | VARCHAR unique    | `SHA-256(raw key)`           |
| `key_prefix`   | VARCHAR(20)       | Safe preview (`ask_live_`)   |
| `name`         | VARCHAR           | Default key label            |
| `last_used_at` | TIMESTAMPTZ       | Updated on ingest            |
| `created_at`   | TIMESTAMPTZ       |                              |

### `monitor_configs`

One row per website URL watched by the uptime monitor.

| Column             | Type        | Notes                    |
| ------------------ | ----------- | ------------------------ |
| `id`               | UUID PK     |                          |
| `project_id`       | UUID FK     | `ON DELETE CASCADE`      |
| `name`             | VARCHAR     | Display name             |
| `url`              | TEXT        | HTTP/HTTPS URL           |
| `interval_minutes` | INT         | Default 5                |
| `is_active`        | BOOLEAN     | Default true             |
| `created_at`       | TIMESTAMPTZ |                          |

### `error_groups`

Grouped summary row per distinct error fingerprint. Repeated ingests
increment `occurrences`.

| Column            | Type         | Notes                                      |
| ----------------- | ------------ | ------------------------------------------ |
| `id`              | UUID PK      |                                            |
| `project_id`      | UUID FK      | `ON DELETE CASCADE`                        |
| `fingerprint`     | VARCHAR(64)  | SHA-256 grouping key                       |
| `exception_class` | VARCHAR(255) |                                            |
| `title`           | VARCHAR(500) | First line / short message                 |
| `level`           | VARCHAR(50)  | `error`, `warning`, `info`                 |
| `environment`     | VARCHAR(100) | `production`, `staging`, etc.              |
| `status`          | VARCHAR(50)  | `unresolved`, `resolved`, or `ignored`     |
| `occurrences`     | BIGINT       | Incremented on repeat                      |
| `first_seen`      | TIMESTAMPTZ  |                                            |
| `last_seen`       | TIMESTAMPTZ  |                                            |
| `trace_id`        | VARCHAR(255) | Optional correlation id                    |
| `created_at`      | TIMESTAMPTZ  |                                            |

Unique constraint: `(project_id, fingerprint)`.

### `security_scans`

Stores Basic Security Analysis results. The feature performs a small
fixed-port TCP exposure check, detects simple service hints, inspects
HTTP information and common security headers when applicable, then
stores a lightweight risk score.

| Column             | Type        | Notes                                      |
| ------------------ | ----------- | ------------------------------------------ |
| `id`               | UUID PK     |                                            |
| `project_id`       | UUID FK     | Nullable for backwards-compatible scans    |
| `target`           | VARCHAR     | Hostname supplied by the user              |
| `resolved_host`    | VARCHAR     | Resolved address / hostname                |
| `scanned_ports`    | TEXT        | CSV list of scanned ports                  |
| `open_ports`       | TEXT        | CSV list of open ports                     |
| `closed_ports`     | TEXT        | CSV list of closed ports                   |
| `status`           | VARCHAR     | `pending`, `completed`, or `failed`        |
| `error_message`    | TEXT        | Failure detail                             |
| `detected_services`| TEXT JSON   | Port-to-service hints                      |
| `http_info`        | TEXT JSON   | HTTP status, server, content type, timing  |
| `security_headers` | TEXT JSON   | Presence of checked security headers       |
| `risk_score`       | INT         | Lightweight score                          |
| `risk_level`       | VARCHAR(20) | `LOW`, `MEDIUM`, `HIGH`                    |
| `summary`          | TEXT        | Human-readable analysis                    |
| `created_at`       | TIMESTAMPTZ |                                            |
| `completed_at`     | TIMESTAMPTZ |                                            |

### `load_tests`

Stores Basic Load Test runs. A run is intentionally capped: maximum
100 requests, maximum 10 concurrency, 5 second per-request timeout,
and a 60 second cooldown per target. Targets must be existing monitor
URLs.

| Column                     | Type             | Notes                               |
| -------------------------- | ---------------- | ----------------------------------- |
| `id`                       | UUID PK          |                                     |
| `project_id`               | UUID FK projects | `ON DELETE CASCADE`                 |
| `monitor_id`               | UUID FK monitors | `ON DELETE SET NULL`                |
| `target_url`               | TEXT             | URL copied from the monitor         |
| `requested_count`          | INT              | Requested request count             |
| `concurrency`              | INT              | Requested concurrency               |
| `status`                   | VARCHAR          | `pending`, `completed`, or `failed` |
| `total_requests`           | INT              | Completed request attempts          |
| `successful_requests`      | INT              | 2xx/3xx responses                   |
| `failed_requests`          | INT              | Non-success or failed requests      |
| `avg_response_time_ms`     | DOUBLE PRECISION | Average latency                     |
| `min_response_time_ms`     | INT              | Minimum latency                     |
| `max_response_time_ms`     | INT              | Maximum latency                     |
| `p95_response_time_ms`     | INT              | 95th percentile latency             |
| `status_code_distribution` | TEXT JSON        | Status-code counts                  |
| `error_message`            | TEXT             | Failure detail                      |
| `created_at`               | TIMESTAMPTZ      |                                     |
| `completed_at`             | TIMESTAMPTZ      |                                     |

### `ai_error_analyses`

Per-project, per-fingerprint cache for AI-generated error
explanations. This prevents repeated calls for the same grouped issue
unless the user explicitly forces a refresh.

| Column                      | Type         | Notes                         |
| --------------------------- | ------------ | ----------------------------- |
| `id`                        | UUID PK      |                               |
| `project_id`                | UUID FK      | `ON DELETE CASCADE`           |
| `fingerprint`               | VARCHAR(64)  | Error group fingerprint       |
| `payload`                   | TEXT         | Stored structured AI response |
| `model`                     | VARCHAR(100) | Model used by the backend     |
| `occurrences_at_generation` | BIGINT       | Error count when generated    |
| `created_at`                | TIMESTAMPTZ  | Cache timestamp               |

Unique constraint: `(project_id, fingerprint)`.

## ClickHouse tables

Created by `clickhouse_schema.sql`.

### `seestack.errors`

Raw error events with a 30-day TTL.

```
id UUID, project_id UUID, fingerprint String,
exceptionClass String, message String, stack_trace String,
level LowCardinality(String), environment LowCardinality(String),
release String, user_id String, user_email String, user_ip String,
metadata String, timestamp DateTime64(3)
```

Engine: `MergeTree() ORDER BY (project_id, timestamp)`.

### `seestack.monitor_checks`

One row per scheduled uptime check with a 90-day TTL.

```
monitor_id UUID, project_id UUID, status UInt8,
response_time_ms UInt32, status_code UInt16,
timestamp DateTime64(3)
```

Engine: `MergeTree() ORDER BY (monitor_id, timestamp)`.

### Additional telemetry tables

The ClickHouse schema also contains tables used by earlier or
supporting observability capabilities:

| Table                    | Purpose                                      | TTL    |
| ------------------------ | -------------------------------------------- | ------ |
| `seestack.logs`          | Structured application logs                  | 14 day |
| `seestack.http_requests` | Inbound/outbound HTTP request telemetry      | 30 day |
| `seestack.cron_pings`    | Scheduled job heartbeat records              | 90 day |
| `seestack.ssh_audit_logs`| Browser SSH command audit history            | 90 day |
| `seestack.replay_events` | Session replay event stream                  | 30 day |

## Seed data

seeStack deliberately ships no required seed data. On first boot the
schema is empty. The normal product workflow is:

1. `POST /api/auth/register` creates a user, a default project
   (`My First Project`), and a default ingest API key.
2. Subsequent SDK ingests populate `error_groups` and
   `seestack.errors`.
3. `POST /api/v1/monitors` populates `monitor_configs`; the scheduler
   populates `seestack.monitor_checks`.
4. `POST /api/v1/security-scans` populates `security_scans`.
5. `POST /api/v1/load-tests` populates `load_tests` for an existing
   monitor URL.
6. `POST /api/v1/errors/{fingerprint}/ai-analysis` populates
   `ai_error_analyses` when `OPENAI_API_KEY` is configured.

## Dropping everything

```bash
cd infra/docker
docker compose down -v
```

The next startup recreates empty databases. The backend then applies
Flyway migrations and initializes the ClickHouse schema again.
